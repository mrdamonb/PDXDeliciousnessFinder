## Deferred from: code review of story 2.9 (2026-09-02)

- ~~**Inbound realtime sync cannot decode anything, for either table.**~~ — **addressed in story 1.5, 2026-09-02 (pending device verification).** `RealtimeSubscriptions.realtimeDecoder` dropped `keyDecodingStrategy = .convertFromSnakeCase`; the explicit snake_case `CodingKeys` on both DTOs already did that job, and the strategy was rewriting keys like `user_id` to `userId` before they reached those `CodingKeys`, so every required key failed to match and decoding threw on the first key. Both empty `catch` blocks now log via `OSLog` instead of swallowing the error. See `1-5-visit-history-survives-reinstall.md`.
- **Optional columns cleared on iOS never reach the server.** `RestaurantDTO.encode` uses `encodeIfPresent` throughout (`Core/Network/DTOs/RestaurantDTO.swift:68` and neighbours), and `SyncQueue.executeUpsert` pushes that DTO as `upsert(dto, onConflict: "id")` (`Core/Sync/SyncQueue.swift:169`). Setting a value to nil omits the key, so `ON CONFLICT DO UPDATE` never touches the column and the stale value survives — and then returns on the next pull, because `pullFromRemote` only applies a DTO when `dto.updatedAt > existing.updatedAt` and the pushed row carries the same local `updatedAt`. Affects `website`, `cuisine`, `general_note`, `menu_url` and every other optional column. Web is unaffected: `EditRestaurantModal` sends an explicit `null`. Fix is to encode nulls explicitly rather than omitting them, which needs a check that no server-side default depends on the omission.
- **The menu URL is not visible on either detail surface.** `RestaurantDetailView.swift:112` renders Website only, and the web panel's details block is gated on `cuisine || address || neighborhood || website` (`RestaurantPanel.tsx:324`), ignoring `menu_url`. A restaurant with a menu URL and no website shows no link anywhere except inside the Add Visit sheet, so there is no way to confirm what was saved without reopening Edit. Story 2.9 put this out of scope deliberately; revisit if the field sees real use.
- **Web create and import paths omit `menu_url`.** `saveRestaurant` (`web/src/app/actions.ts`), `AddRestaurantModal.tsx` and `ImportModal.tsx` do not carry the field. They already omit `website` too, so this is the pre-existing create-path gap widening rather than a new divergence — but iOS Add Restaurant now sets a menu URL and web cannot.
- ~~**SwiftData migration has never been exercised against an existing store.**~~ — **triggered and patched in story 2.10, 2026-09-06.** This stopped being theoretical the moment `VisitLog` (which already has real rows in installed local stores) got a new non-optional `updatedAt` property with no inline default. Fixed by declaring `var updatedAt: Date = .now` at the property level, matching SwiftData's documented pattern for safe lightweight migration of new non-optional properties. Still worth a real `VersionedSchema`/`SchemaMigrationPlan` eventually — this patch avoids the immediate crash risk but doesn't add the missing infrastructure — and still needs confirming by launching the 2.10 build over an existing install with real visits, not a clean one.

## Deferred from: code review of story 1.5 (2026-09-02)

- **Hydrating the relationship arms the cascade delete rule for the first time.** `Restaurant` declares `@Relationship(deleteRule: .cascade, inverse: \VisitLog.restaurant)` (`Core/Storage/Models/Restaurant.swift:75`). Until story 1.5, synced visits had a nil relationship, so the cascade never reached them. Now that both inbound paths hydrate, deleting a restaurant removes its local visits — while `RestaurantRepository.delete` enqueues no matching remote visit deletes, so those rows survive server-side and return on the next pull. New behaviour introduced by 1.5, not a defect in it. Worth deciding deliberately: either cascade remotely too, or stop cascading locally.
- **The visit pull is insert-only.** No update path: a note edited server-side never reaches the device, because `handleVisitLogChange` treats `.update` as a no-op ("visit logs are immutable") and `pullFromRemote` skips any row it already holds. No delete reconciliation either: a visit deleted elsewhere is removed locally only if a realtime delete event lands, and by this story's own account none ever has — so devices are likely holding visits that no longer exist server-side, and the new pull will never remove them. `RestaurantRepository.pullFromRemote` at least compares `dto.updatedAt > existing.updatedAt`; `visit_logs` has no `updated_at` column to compare against.
- **The visit pull skips the `hasPendingOperation` guard that both realtime handlers apply.** If a queued local delete has not flushed — `flush()` early-returns when already flushing or offline — the pull re-inserts the row the user just deleted, and the later flush deletes it remotely, leaving a local ghost. Pre-existing asymmetry between the pull and realtime paths; worth either fixing or documenting at the pull site.
- **No pagination on the visit select.** `.select()` with no `.range` is subject to PostgREST's `max-rows` ceiling, which truncates silently rather than erroring. There is also no incremental filter, so every foregrounding refetches the entire visit history. Restaurants are bounded by hand-entry; a food journal is not.
- **`hydrateRestaurant(for:)` is duplicated verbatim** in `VisitLogRepository.swift` and `RealtimeSubscriptions.swift`, and `Logger(subsystem: "com.damonbrennen.PDXDeliciousnessFinder", …)` is now hardcoded in a third file alongside `SyncQueue.swift` and `PlacesEnrichmentService.swift`. Story 1.5 chose "hydrate at the insertion site" over threading a `ModelContext` into `toModel()`, which was the right call for size, but nothing was done about the known downside. A shared helper plus a subsystem constant next to `SupabaseTables` would match the convention ARCH-10 already sets.

## Deferred from: code review of story 2.10 (2026-09-06)

- **Editing a visit while a fresher remote edit has just landed can silently clobber it.** `AddVisitView`'s edit sheet captures `visitedAt`/`note` into `@State` at `init` time. `hasPendingOperation` (checked by the realtime handler) only guards against an *inbound* update overwriting an unflushed *local* write — it does not protect the reverse direction. If a realtime `.update` for the same visit arrives and applies while the sheet is still open, then the user taps Save, the save unconditionally writes the sheet's stale in-memory values and stamps a new `updatedAt`, so the local save "wins" by wall-clock time even though the user never saw the newer remote content. Matches the deliberately simple last-write-wins model the spec chose (no live conflict UI), but the specific "sheet open across an inbound edit" window isn't covered by anything.
- **Editing a visit whose realtime delete arrives while the sheet is open leaves a dangling reference.** `editingVisitLog` in `AddVisitView` is a live `@Model` reference; if it's deleted out from under the sheet, tapping Save calls `VisitLogRepository.update` on a removed object with undefined behavior. Same class of issue already deferred from story 2.8's review for `PickRestaurantView`'s selected restaurant, and currently unreachable for the same reason: realtime deletes do not work yet (see the 1.5 review). Revisit once realtime deletes are fixed.
- **`HistoryView`'s `.editVisit` case silently renders nothing if `log.restaurant` is nil** by the time the sheet presents (`case .editVisit(let log): if let restaurant = log.restaurant { AddVisitView(...) }` — no `else`). Same currently-unreachable class as above (requires the restaurant to vanish locally between the swipe and the sheet rendering), but if realtime deletes start working this becomes a blank, undismissable-by-content sheet rather than a crash.
- **`SyncQueue.onPermanentFailure` is declared and never assigned.** After 3 failed retries, `SyncQueue.flush()` calls it and then unconditionally deletes the operation (`SyncQueue.swift:109-116`) — but nothing is listening, so a permanently-failing push (sustained network loss, an unexpected RLS denial, etc.) silently disappears with no user-facing error. Pre-existing gap across the whole sync layer (already true for restaurant updates and visit inserts/deletes), not introduced by story 2.10 — but 2.10 is the first time a *user-initiated edit* can be silently dropped this way, which is exactly the failure mode the story's own RLS caution called out. Worth wiring to a real error surface (toast, retry banner) rather than fixing per-call-site.
